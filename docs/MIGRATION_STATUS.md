# NeoForge port audit and repair status

Updated 2026-10-23. This is a maintained, unofficial reconstruction. It builds, but it is **not yet a faithful replacement for the original gun engine**. The first source audit identifies substantial omissions; the tested fixes below do not certify every subsystem.

## Pinned references and recovery history

- Gameplay reference: official Create: Love & War `0.4.2-1.20.1-Create-6.0.6`, Modrinth version `1FjYbLl5`.
- Original engine dependency inspected: Flan's Mod Reloaded `0.4.316`, compatible with the official release's declared dependency range. Historical players may have used different dependency versions.
- Recovered port baseline: `1.0.9-1.21.1`, input SHA-256 `3cb2032a80019661c388c5204a6ec1c5899d8e743b168f47560fb465d1c6d4bb`.
- Commit `6767017`, tag `recovered-1.0.9`, preserves all 194 recovered Java units before fixes. All 194 were compared against the untouched decompiler output, ignoring line-ending representation only: zero missing or changed files.
- Commit `0b96e69` contains compilation reconstruction separately from behavioral repairs: generic types, interface default-method calls, ambiguous nested types and the obsolete VecHelper import.
- Java 21; Minecraft 1.21.1; NeoForge 21.1.253; Create 6.0.10-280. See [reference-manifest.json](reference-manifest.json) for download URLs and hashes.

## Gun crafting reference decisions

Reference paths: Flans `GunFabricationRecipe`, `GunCraftingOutputSlot`, `WorkbenchMenuGunCrafting`, `AbstractWorkbench` and `FlanItem` from the pinned dependency. Three baseline GameTests failed for missing selection, shapeless matching and bare results before repair.

- Original gun crafting is immediate. `craft_time` is serialized (default 20) but does not drive a gun countdown; the original countdown path belongs to part crafting. Existing saved NeoForge countdowns are finished once into real output storage; new crafts use a computed preview.
- **Quirk kept:** input order matters, extra unused slots are ignored for consumption, but every recognized part stack in the input inventory contributes one canonical part ID. Stack count and arbitrary input NBT are not copied into provenance. The output slot yields one gun per take even if a custom recipe declares a larger result count.
- **Quirk kept:** the official `gun_fabrication/stg57_scope` recipe produces `optical_scope`, which no authored bench allows. The remaining 45 recipes are allowed by at least one of the six benches. The recipe and filters are unchanged; the regression test identifies this exact orphan rather than treating it as an inaccessible gun.
- The six authored benches enable modification but do not enable painting. Removed the replacement's free paint-cycle button/request. Magazine upgrade parity remains separate work.
- UI adaptation: stable recipe-ID order with paged choices; click an empty ingredient slot to auto-fill, or Shift + right-click to refill/cycle. Survival transfer validates capacity before returning an existing stack, preventing the original partial-insertion loss risk. Creative cycles matching material variants.
- Previews are transient menu data and never saved/dropped as inventory. Normal pickup, hotbar swap, shift-click/full-inventory refusal, stale/distant requests, breaking a previewing bench, item/recipe serialization and unused-part contribution have regression coverage. The catalog is built once per open menu; assembled previews are cached until inputs or recipe identity change. These are structural reductions in repeated work, not a measured end-to-end performance result.

## Trait reference decisions

- Flans `FlanItem.GetTraits` combines part trait providers and installed attachment `abilities` providers, with an upper cap after each provider. Attachment `abilities` is a list of `{trait, level}` references, not inline trigger definitions. Unknown definitions do not contribute. Canonical bare and `traits/`-prefixed references identify the same trait.
- `GunTraits` now resolves that data from the saved component. Tooltips show the summed/capped level, original localized name/colour/description and expanded crafting inputs. All 78 authored part definitions have empty direct modifier lists, and all 49 gun definitions have empty static ability lists; the UI repair does not establish execution of every optional field.
- **Quirk kept:** no call site in the pinned Flans sources dispatches `EAbilityTrigger.AlwaysOn`. `AbilityTriggerDefinition.Matches` requires exact trigger identity. Such declarations are not automatically active stat modifiers; the target's unconditional shortcut was removed. This corrects the initial audit's implication that all declared material modifiers must affect shooting. It is not proof that all trait-triggered paths are implemented.
- The active equip path is `ServerActionManager.ServerTick` -> `ActionStack.UpdateEquipped` -> `EvaluateTrigger` -> `AbilityEffectApplyAttribute.TriggerServer`. The target checks both hands on server player ticks and applies a transient modifier with a shared effect identity. An unchanged equipped stack does not repeatedly resolve definitions or add modifiers. This was not an end-to-end performance benchmark.
- **Quirks kept:** the original passes a null `AbilityStack` for a nonstackable effect, so `PerLevel` defaults to one; Stoic II still adds 1.0 toughness. `attribute_multiplier` uses attribute **addition**, not multiplication. `ActionStack` does not evaluate `endTriggers`, and `AbilityEffectApplyAttribute.EndServer` is empty, so the transient bonus remains after unequip. The effect identity prevents equipping another gun with the same trait from duplicating it. Tests cover these cases explicitly.
- Shot/reload mob effects, conditional triggers, general stack lifecycles and additional ability effect types remain open. The three authored triggered mob-effect traits refer to `flansbasicparts` IDs; that optional content is not registered by the pinned Flans JAR itself. Missing effect definitions must not be replaced with invented buffs.

## Firing cadence reference decisions

- Compared pinned Flans `ActionManager.KeyPressed/KeyHeld/KeyReleased`, `ActionGroupInstance.DoInitialTrigger/CheckRetrigger/UpdateInputHeld/Finished`, `ActionStack.TryShootMultiple/OnTick` and `ShootAction.CanRetrigger`, including the owning-player network path. The only authored BurstFire group is G11 `primary_fire`: repeatCount 3, repeatDelay 0.055 seconds, with a 0.75-second animation.
- Original fractional cooldown is decremented/clamped per tick, and each positive-delay trigger adds delay * 20 until cooldown reaches at least 1. The G11 therefore triggers on ticks 0/1/2; MAT-49's 0.1-second interval triggers on ticks 0/2/4. Fractional remainder is retained between presses rather than rounded away. Unit tests also cover sub-tick multi-trigger rates and zero-delay initial actions.
- **Quirks kept:** BurstFire decrements its remaining retrigger checks once per tick, including failed/no-ammo checks; release does not cancel it. A positive-delay burst gets repeatCount - 1 checks after its initial trigger; zero-delay initial triggering does not schedule them. Group duration is floor(max(repeatDelay, authored action durations) * 20), and SemiAuto/BurstFire end when progress exceeds duration * trigger count. Retriggering an existing group retains progress and increases its trigger count. Declared animation lifetime is not an extra cooldown that prevents a fresh burst press.
- **Protocol adaptation:** the original owning client schedules triggers and forwards them. This port now schedules repeats on the server from input edges. Duplicate/legacy held packets do not create new semi-auto/burst presses. Full auto keeps firing without per-shot client requests and stops on release, including a release arriving after selecting an empty hand. Normal 20 TPS cadence is source-derived and tested; latency/divergent client/server TPS remains unverified.
- Action stacks continue ticking for inventory guns after a hotbar switch, as in `ServerActionManager.ServerTick`. Runtime controls are held outside saved item components, discarded on logout/server stop, and pruned when inventory ticking ceases. Reload interrupts retriggers; dropped/reloaded stale firing metadata cannot resume a phantom burst. Dead/spectator owners are prevented from continuing scheduled fire.
- Client animation/flash confirmation observes the growing group trigger duration, so repeated server shots restart their effect instead of requiring another local press. The deterministic animation-state test verifies this restart; full model/FX parity remains on the rendering queue.
- Safety deviation for malformed content: cap generated triggers at 64 per tick and clamp extreme sub-tick intervals to that bound. No authored interval approaches this limit. The runtime caches resolved group/attachment data during a firing cycle and publishes one immutable firing-frame state per tick; this is not a broad performance certification.

## Action audio reference decisions

- Compared pinned Flans `PlaySoundAction`, `SoundLODManager`, `SoundDefinition`, `SoundLODDefinition` and action-group context/propagation. The recovered port already registers `flansmod:gunshot_slam`; the initial suspicion that it was silent because of missing registration was disproved by a runtime check. The confirmed baseline failures are the players/hostile category mismatch and default range 16 versus 100.
- Original `PlaySoundAction` uses `SoundSource.HOSTILE`, a fixed-range sound event and delayed local playback. Each receiving camera entity chooses the greatest positive LOD threshold at or below its distance; equal thresholds retain the first authored entry. Sound definitions default to length 1, range 100 and `flansmod:null`; LODs default to distance 100 and the same invalid ID. Bundled sound LOD arrays are empty, so the client near/far scenario uses a clearly synthetic definition with existing assets.
- Volume is the original **unclamped** linear interpolation from maxVolume at distance zero to minVolume at maxRange. Only pitch is randomized. Action-group `loudness` and `pitch` modifiers multiply playback; the authored silencer produces volume factor 0.25 and pitch factor 4. The client backend observations report requested sound-instance pitch; Minecraft's sound engine applies its own final pitch clamp.
- **Protocol adaptation:** the server now sends a sound definition, shooter eye position and resolved group multipliers; clients resolve their own camera distance and random pitch before calling local playback. The original transmits action triggers and reconstructs playback client-side. PlaySound actions retain the original 200-block action propagation floor, tested with recipients at 199/201 blocks. Fixed-range event metadata and action propagation do not establish audibility at those distances: asset attenuation still applies. Moving-shooter interpolation, latency and dedicated observers remain unverified.
- Both normal firing and reload-stage sound calls use the gun stack's actual attachments. A real G11 burst produced three backend submissions in the hostile category at volume 1; its silenced counterpart produced three at volume 0.25 with the authored pitch multiplier. Synthetic 2/12-block requests selected slam/snap respectively, with delayed far playback. The observer uses NeoForge's source event after buffer attachment and channel playback; this is backend evidence, not a listening assessment. Diagnostic commands/listeners are opt-in and excluded from release artifacts.
- Action offsets are still executed immediately by the recovered action runner. Restoring audio interpretation does not establish action scheduling parity.

## Projectile reference decisions

- Compared pinned Flans `ProjectileDefinition`, `TrailDefinition`, `HitscanDefinition`, `ShootAction`, `GunshotContext`, `BulletEntity`, `BulletGuidance`, `GunItem.HandleLock` and bullet renderers. Original Flan's Mod/Physics metadata credits jamioflan and declares MIT. Original Love and War credits remain unchanged.
- Restored `flansmod:bullet` as a distinct 0.5-block entity with the original tracking range. `createloveandwar:shot_projectile` and its 0.25-block bounds remain for Robotdog. Gun impacts no longer depend on a transient global map keyed only by entity integer ID. Firing processes every hitscan/projectile definition and uses the original ceiling for modified shot counts.
- Projectile and trail codecs now retain acceleration, maximum speed, lock/track cones/range/time, top-attack fields, target categories and underwater flags. Defaults match the pinned definitions. Shared core penetration defaults to the original hitscan zero; the original projectile definition does not consume its authored penetration field. Decoding these fields alone is not a runtime parity claim.
- **Quirks kept:** `ShootAction.Calculate` builds a trajectory scaled by launch speed, then `ServerSpawnBullet` multiplies it by launch speed/20 again. The reconstruction follows that source chain: speeds 1/3/6/8/9 produce 0.05/0.45/1.8/3.2/4.05 blocks/tick. Ten bundled projectile variants are tested. These are source-derived oracles; a live original-engine trajectory comparison remains required.
- Tick order is acceleration, drag, gravity, collision response, guidance, movement, facing, fuse and client trails. Acceleration adds acceleration/20 while speed is below maxSpeed/20 and can overshoot. Drag clamps its factor to [0,1]; gravity subtracts gravityFactor * .02. Original block bounce/stick/pass-through/detonate behavior and lack of an arbitrary 80-tick expiry are retained. A no-gravity stationary penetrating Gyrojet with its authored 400-second fuse survives beyond tick80. Black-powder gravity is authored 0.1, not the definition default 1. Original `responseToVehicle`, legacy air/water particle strings and particle interval are not called by the inspected projectile tick path; trail definitions drive emissions.
- Original lock acquisition scans the authored category order within a cube, chooses the closest visible candidate inside a strict angle, and confirms after **more than** lockTime ticks. A retained candidate only rechecks angle. The reconstruction preserves these rules, the simple/predictive/beam/top-attack steering paths and the empty projectile reacquisition method. Top attack retains its original lack of a track-cone check and uses its original three-block forward waypoint. Basic/top attack and lock threshold/retention are runtime tested; additional steering modes have source coverage but still need scenarios.
- **Protocol adaptation:** selected-gun lock state is owned by the server and scoped to the held stack/player, rather than mutable fields shared by every stack of the original item singleton. Clients do not supply a target ID. Lock HUD/feedback is still missing. The replacement has no Flans vehicle subsystem; the unused `vehicle` target category matches nothing, and custom explicit entity IDs currently match that type rather than the original registry base-class behavior. All authored lock-on rounds use flyingMob/monster/living categories, which are implemented.
- **Inherited defect fixes:** save/reload preserves remaining fuse/age and uses a target UUID instead of resetting the fuse through InitContext or persisting a stale runtime ID. Missing definitions are discarded safely; malformed entity-bounce responses pass through rather than casting an entity hit to a block hit. Zero-length steering vectors and floating-point dot products are guarded against NaN. On 1.21.1 an explicit empty collision context replaces the original null entity context.
- Resolved physics/response/visual parameters and model identity are synchronized; full impact modifiers and calculation inputs remain in server memory and entity saves. Firing-cycle progress is used for fuse initialization. **Quirk kept after follow-up review:** original active `ModifierCache` and effect `StatHolder` paths never call `ModifierDefinition.AppliesTo`; declared matchGroupPaths do not filter either firing or effect modifiers. The replacement's numeric/override filtering was removed and complete modifier lists survive the snapshot. Unit and saved-impact cases cover nonmatching declarations. Snapshotting parameters at launch is a current adaptation; original contexts can resolve stats dynamically from the gun. Reloadable definitions/live modifier changes during flight remain on the infrastructure/trait queue. Entity NBT round trips and repeated-detonation guards are tested; a full server restart with in-flight rounds remains unverified.
- Client rendering uses each bullet's authored mesh, bypasses held-item icon transforms/local muzzle-flash state and unwraps animation models for trail attach points. A real penetrating Gyrojet was observed at age83 after the click/network path. Four stationary showcase bullets displayed distinct authored meshes (6/6/18/18 quads); server/client identity and positions agreed. A follow-up run with particles enabled visibly emitted smoke/poof effects around the showcase, and its screenshot was inspected. The prior minimal-particle screenshots do not establish emissions. Original/target particle alignment, model orientation/scale, guided motion under latency and dedicated observers still need validation. The private client's original options were restored after testing.
- Four failing physics/lifetime baselines and three failing codec baselines are retained privately from the unchanged e5fb1f9 production sources with added regression fixtures. Initial fixtures assumed the wrong black-powder gravity and fuse-bearing round; corrected cases were rerun against that baseline. A larger isolated test arena avoids the tiny template's barrier walls/unloaded neighboring target chunks; this was a fixture repair, not a gameplay change.
- Follow-up read-only reviews found reversed particle root rotations, MISS dispatch incorrectly invoking ShotBlock effects, declared path filtering and effects using the owner's current dimension. Failing numeric trail/filter tests and two failing runtime tests were retained, then corrected. Trails now follow `Transform.quatFromEuler`'s negation of all supplied Euler angles. Fuse misses dispatch ShotPosition only. **Robustness fix:** impacts stay in the projectile's world after its owner changes dimensions, rather than following the owner into another world.
- Follow-up accumulation-input repairs are described below. Equal-distance ties inside expanded flyingMob/monster categories still need the original per-class priority. Sending complete impact context to clients is unnecessary for local physics/rendering; the opt-in setup profile measures allocation, CPU and actual metadata encoding, and the compact representation is implemented/tested as described below.

## Stat accumulation inputs

- Pinned `StatAccumulator.Calculate` uses the gun's installed attachment count. `FlanItem.GetAttachmentStacks` counts every nonempty stored stack once, regardless of item count or recognized definition. A separate calculation-input source now carries that count through normal firing, sound, equipped attribute effects and impact source composition; it is not inferred from modifier IDs or the number of valid definitions. Attachment-less/out-of-context calculations use zero.
- **Quirk kept:** the active `IStatCalculatorContext` has no `GetMagFullness` override. The separate legacy `StatCalculationContext` helper does not supply the active formula path. `PerMagFullness` therefore resolves to zero and `PerMagEmptiness` to one even for a loaded gun. Both fields now decode correctly. Nonstackable `PerLevel`/`PerStacks` defaults remain one, and repeated input declarations apply once as in the original formula's bit flags.
- Projectile context saves the attachment count alongside its modifiers, so both firing-source and effect-local `PerAttachment` values survive an entity NBT round trip. Older reconstruction snapshots lacking the field fall back to zero; their original count cannot be recovered from the flattened modifier data. Launch-time snapshot versus live changes remains a documented adaptation.
- Three runtime regressions (launch/saved impacts, sound multipliers and duplicate flags) and two unit regressions (zero attachments and magazine input decoding/defaults) failed before repair. The corrected fixture isolates synthetic modifiers from the G11's existing damage bonus. Zero/two attachment slots, unknown definition stacks, empty slots, item stack counts, source/effect composition and original default inputs now pass. These are synthetic compatibility cases: no bundled active projectile modifier uses these scalars.
- [The opt-in profile](PROJECTILE_PROFILING.md) runs in a real NeoForge server and records JFR plus exact thread allocation/CPU counters and metadata packet sizes. It measures projectile setup only; representative gameplay profiling remains open. The measured compact-context optimization reduced median setup allocation from 61,662 to 11,219 bytes/projectile and median server-thread CPU from 12.5 to 4.7 microseconds in the recorded same-environment workload. Uncompressed metadata shrank from 997–1,550 to 191–593 bytes. All samples and limits are documented in the profile guide; this does not certify battle TPS/FPS or first-save cost.

## Verification boundaries and release criteria

- Current evidence is strongest for the small repaired paths with failing baseline tests.
- Machine operation, gun parity, natural worldgen, multiplayer and full-pack interactions remain partially or wholly unverified.
- No new JAR was installed into Prism or the remote server. No saves or existing pack snapshots were replaced.
- Packaging uses stable archive ordering and fixed timestamps. After normalizing the recovered working copy to the existing Git LF policy (no Git content change), `--no-build-cache clean build` in the checkout and a fresh Git source export under another directory produced identical mod and source SHA-256 hashes. Both independently executed their compilation/resource/test tasks. This verifies same-environment rebuilds from committed source; cross-machine/JDK reproduction remains unverified.
- Keep the experimental artifact out of a public release until the P1 queue and representative original/target scenarios are resolved. Publication remains a later, separately requested action.
